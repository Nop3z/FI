# 方法论：逆向先行（2026-11-09 用户纠偏，最高优先级）

## 用户原话（项目纪律，高于任何排期）

> "有一个需要注意的 就是要逆向先行，先逆向出来理清楚再写什么拦截器之类的，要不然干很多无用功。要先反汇编明白。比如我提前说好我要故障注入这颗芯片 ISP 模式下的 write，然后先去逆向出整个 write 实现的流程，然后构造好完整的调用链，评估运行时间调整 delay，然后后面试运行看看能不能打出什么错误来，然后才是反馈之类的。"

## 由此确立的正确工作顺序（不可颠倒）

1. **声明目标**：先明确要打的**具体功能点**（例：ISP 模式下的 write）。
2. **静态逆向该功能**：反汇编定位它的完整实现——入口、调用链、每层函数、关键分支、错误码出口、协议帧构造。
3. **构造完整调用链**：从复位/入口到目标指令的**可达路径**，逐层标注地址与条件。
4. **评估运行时间**：估算链路上每段耗时，映射到 delay/pulse 的可搜索窗口（不是盲扫）。
5. **构造注入点**：基于 2–3 的结论挑选精确靶点（指令地址 + 期望扰动），**不是先写通用拦截器再找地方用**。
6. **试运行验证**：跑仿真/实机，看能否打出预期异常（错误码/帧/行为差异）。
7. **反馈与分析**：根据结果修正逆向结论与参数，再迭代。

## 反面模式（禁止）

- ❌ 先造通用拦截器/Provider/框架，再回头找用途——**干了很多无用功**。
- ❌ 参数空间盲目全扫（例：直接扫 delay 27000–38000 全区间）而不先算出"该打哪条指令、它在大致什么时刻执行"。
- ❌ 只做静态命中统计（"某错误码在 ROM 出现 N 次"）就算完成逆向——必须理清**调用链与可达性**。

## 对当前工作的影响（2026-11-09 重新排序）

| 项 | 原优先级 | 新优先级 | 说明 |
| --- | --- | --- | --- |
| ISP write 功能完整逆向 + 调用链 | 未列 | **P0** | 立即启动，用户指定的首个目标功能 |
| 运行时间评估（指令→时间映射） | 未列 | **P0** | delay 调参的前提；仿真目前只有指令序号、无周期估算，需补 |
| 目标靶点精确构造 | P1 | **P0** | 基于调用链而非盲枚举 |
| 试运行打出预期错误 | P1 | **P0** | 闭环的验证点 |
| 通用 discover 基础设施 | P0 | P2（降级） | 已建的 regions/traps/targets 保留，但**不再优先扩展**；它们服务于逆向，不是目的 |
| 轨迹分级/吞吐优化 | P0 | P2（降级） | 够用即可；等逆向跑通再优化 |
| UI 契约/通报 | 持续 | P3 | 不阻塞 |

## 已有资产如何服务这个顺序

- `fi discover traps`：已能定位 mtvec/handler——**逆向 P0 的第 2 步（找异常出口）直接用**。
- `fi discover targets`：已能枚举错误码装载点与共享发送函数——**第 2/5 步直接用**（0x<ADDR> 已确认 19 调用点）。
- `fi discover regions`：定位 RAM/MMIO——**第 3 步构造可达路径时直接用**。
- 仿真 `inject`（skip/flip_reg_bits/reg_write/mem_write）：**第 6 步直接用**。
- 缺的：**功能级调用链重建**（从"我要打 write"到"地址序列"）与**周期估算**——这是新增 P0。

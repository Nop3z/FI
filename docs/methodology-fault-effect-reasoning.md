# 方法论补完：从"打中了"到"为什么"（2026-11-09，读 hn security 文章后）

来源：https://security.humanativaspa.it/fault-injection-down-the-rabbit-hole/（Maurizio Agazzini, 2024-11-13）
归档：https://web.archive.org/web/20250112224512/https://security.humanativaspa.it/fault-injection-down-the-rabbit-hole/

## 一句话

在此之前我们解决的是"**打中了哪条指令**"（归因）；
这篇文章指出了下一层也是真正的目标：**"这条指令被打坏后变成了什么，为什么会产生这个观测结果"**。

文章的核心箴言来自 Raelize 的 TAoFI 课程：**"Don't glitch and pray"**。

## 文章的完整方法论（七步）

1. **减少噪声**：用汇编而非 C，排除无关调用与上下文污染；用 GPIO 寄存器直写（`GPIO_OUT_W1TS/W1TC`）代替函数调用做 trigger。
2. **获得干净上下文**：故意写不可写区域触发 CPU 异常（如 `s32i.n a2, a13, 0`，a13=0x93939393），一次拿到完整寄存器现场。所有故障类型统一用这一种方式，便于统一解析。
3. **指令标记**：给每条目标指令不同的立即数增量（0x1/0x2/0x4/0x8/0x10/0x20/0x40），
   使最终寄存器值**直接编码**"哪几条指令生效了"。这是"精确归因"的最强手段。
4. **触发窗口**：trigger 拉高 → NOP 传播 → 目标指令区 → NOP 保护 → trigger 拉低 → 触发异常。
5. **结果五色分类**：
   - 绿：PC 正确 + 寄存器全对 → 正常
   - 品红：重启 → 毛刺过长
   - 黄：PC 错 → 没走到目标代码
   - 青：PC 正确 + 目标寄存器正确 → 打到了但没影响目标指令（打了别的）
   - **红：PC 正确 + 目标寄存器错 → 命中了目标指令**（唯一有价值的一类）
6. **位翻转假设**：crowbar-to-ground 的物理效果是**把某些 1 变成 0**（不是"跳过指令"）。
   假设一次翻转 N bit，枚举所有可能，得到"损坏后的指令"集合。
7. **仿真复现解释**：把枚举出的损坏指令放进仿真器（文章用 Ghidra P-Code，因为 Unicorn 不支持 XTensa），
   跑出寄存器结果，与实测逐项比对，从而**解释**每个红色样本的成因。

文章明确了 7 个"故障等级"（Level 1-7），从"单指令被打成本质无效的 addi"到"两条指令同时损坏、源/目的寄存器都被改写"。

## 对我们项目的直接启示

### 已有能力（对应文章步骤 3 的一半）
- 我们已有：错误码 → 命令 → handler → 装载指令的静态归因
- 我们已有：trap 机制（38 寄存器帧、mcause 分类）—— 对应文章步骤 2
- 我们已有：Unicorn 指令级仿真 —— 对应文章步骤 7（且 RISC-V 比 XTensa 幸福得多，Unicorn 原生支持）

### 关键缺口（必须补）
1. **位翻转枚举器**：给定指令字节，枚举"1→0"翻 N bit 后的所有变体，反汇编并标注语义变化。
   （对应文章作者的 `opcode_calculator.py`）
2. **故障效果推演**：把损坏指令放进仿真，算出寄存器/内存变化，与预期对比。
3. **观测结果反解**：给定"观测到的寄存器差异 + PC"，反推最可能的损坏指令集合。
4. **五色分类器**：把历次实验的观测按绿/品红/黄/青/红分类，聚焦红色样本。

### 与现有设计的衔接
- 五色分类可直接作为 `AnalysisResult` 的一种 `analysis_kind`（如 `fault_effect_class`）。
- 位翻转枚举结果需带 `confidence=hypothesis`（是候选解释，不是已证实的物理过程）。
- 观测反解必须保留"多解"：多个损坏指令可能产生相同观测，不得只报一个。

## 与我们项目的定位关系（重要）

这个方法论证明了用户此前反复强调的几点：

| 用户此前的说法 | 文章对应 |
| --- | --- |
| "逆向先行，别先造拦截器" | 先搞清要影响哪条指令、什么上下文 |
| "构造完整调用链、评估运行时间调 delay" | trigger 窗口 + 时间定位 |
| "不是 lab toy，要通用" | 方法可迁移到任意目标（文章从 ESP32 出发但方法通用） |
| "区分观测/推断/未知" | 红/青/黄分类正是"能证实的 vs 只是跑飞了"的区分 |

**结论：我们的工具集应该把"位翻转→效果推演→观测反解"做成核心能力，而不是停留于静态归因。**
